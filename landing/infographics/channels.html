Layer 0 · Channels

Talk to your company from any chat app

A channel runtime (opc/channels/) routes external messages into the engine and sends replies back. Each provider is an optional adapter with its own dependency, credentials, and — for some — a companion bridge. Metadata lives in provider_registry.py.

1

Three ways a provider connects

🔌

socket

A live socket the provider pushes to — Slack, Discord, Feishu, DingTalk, QQ.

🔁

polling

OpenOPC pulls for new messages — Telegram, Email, Matrix.

🌉

bridge

A separate companion service you run; OpenOPC connects to it — WhatsApp, Mochat.

Setup flow & messaging semantics

Wire a provider in 6 steps

1. opc init   2. install the extra   3. edit channel_config.yaml   4. set allow_from   5. opc channels login <p>   6. opc channels start -p demo (or opc run)

How messages flow

inbound→ UserMessage→ engine→ SystemMessage→ reply

Session ids derive from provider chat/thread context when available.

Security — deny by default. Inbound sender allow-lists (allow_from) are enforced before a message is accepted. An empty allow_from denies everyone — you opt senders in, never out. Bridge providers additionally need their companion service running (OpenOPC does not manage it).
